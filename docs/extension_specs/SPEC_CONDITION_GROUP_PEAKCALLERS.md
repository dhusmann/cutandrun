# SPEC_CONDITION_GROUP_PEAKCALLERS.md

Summary

This SPEC defines how to implement TODOs 1–3 from docs/extension_specs/TODO.md in the dhusmann/cutandrun fork:
	1.	Add condition to the samplesheet (biological condition, e.g. Control vs Treatment).
	2.	Add group-specific handling for:
	•	Normalization
	•	Peak calling
	3.	Add additional peakcallers (with the defaults/variants described in docs/extension_specs/TODO_PeakCallerExtension.md, plus GoPeaks):
	•	GoPeaks (narrow + broad)
	•	epic2 (3 parameter variants)
	•	SPAN / OMNIPEAKS (2 parameter variants)
	•	MACS2 (narrow + broad)

The design is intended to be compatible with the nf-core/cutandrun architecture and conventions (DSL2, modular processes, schema-driven params, MultiQC reporting), while introducing a richer experimental-design model to support condition-aware and group-aware processing.

⸻

Context: current pipeline behavior (baseline)

Samplesheet

The current nf-core/cutandrun samplesheet format is (at minimum) the columns:
	•	group
	•	replicate
	•	fastq_1
	•	fastq_2
	•	control (IgG/control group name)

Example shown in pipeline docs.

Normalization (today)

Normalization is global (applies uniformly to all samples) and configured via --normalisation_mode with modes including Spikein (default), RPKM, CPM, BPM, None.  ￼

Peak calling (today)

Peak calling currently supports SEACR and MACS2 via the peakcaller parameter, can use control samples by default, can be disabled using --use_control, supports manual control scaling via --igg_scale_factor, and can run multiple callers with comma-separated values (first caller used for downstream; others output-only).

Outputs (today)

Peak calling outputs live under the 03_peak_calling/ results tree, including:
	•	BigWig coverage: 03_peak_calling/03_bed_to_bigwig/*.bigWig  ￼
	•	Called peaks: 03_peak_calling/04_called_peaks/ (SEACR + MACS2)  ￼
	•	Consensus peaks are generated by merging replicate peaks within the same experimental group and can be filtered with --replicate_threshold.  ￼
	•	Peak-based QC includes peak counts, reproducibility, FRiP.  ￼

Goals

Functional goals
	1.	Samplesheet supports condition such that samples can be partitioned into group × condition × replicate.
	2.	Normalization can be computed/handled per group and/or per condition (configurable), without breaking existing global behavior.
	3.	Peak calling becomes condition-aware and group-aware, including control/IgG handling (pooling/matching where needed) and consensus peaks computed per relevant strata.
	4.	Add new peak callers and variants with standardized outputs and reporting:
	•	MACS2 narrow + broad
	•	epic2 200/150/25 bp variants
	•	SPAN/OMNIPEAKS default + stringent variants
	•	GoPeaks narrow + broad (--broad supported by GoPeaks)  ￼
	5.	Preserve nf-core-like conventions:
	•	parameters in nextflow.config with defaults
	•	update nextflow_schema.json via nf-core schema build
	•	add validations / helpful errors
	•	update MultiQC parsing where relevant

Non-goals (explicitly out of scope for this SPEC)
	•	Differential peak calling workflows (TODO #4)
	•	--compare_norm_methods / --compare_peak_callers modes (TODO #5–6)
	•	Downstream enrichment characterization (TODO #7)

(We will ensure the new data model and outputs make TODO #4–7 straightforward later.)

Definitions / data model

We standardize the internal metadata model emitted by the samplesheet parsing step.

Key fields
	•	group: biological target grouping (e.g., histone mark / factor / assay target)
	•	condition: biological condition label (e.g., Control, Treatment, WT, KO)
	•	replicate: integer replicate index
	•	is_control: boolean (true for IgG / control rows)
	•	control_group: name of control group referenced by target rows (existing control column semantics)
	•	sample_id: unique ID for each row, used in filenames and MultiQC

Constructed IDs

If the samplesheet does not provide an explicit unique sample name column, generate:
	•	sample_id = "${group}_${condition}_rep${replicate}" for target samples
	•	sample_id = "${group}_${condition}_rep${replicate}" for control samples as well

This prevents collisions when the same group appears under multiple condition values.

TODO 1: Samplesheet update — add condition

1.1 Samplesheet schema changes

Add a new column:
	•	condition (string; required for all rows unless legacy mode is used)

Backward compatibility strategy
Support two modes:

Mode A: New samplesheet (recommended)
	•	condition column present
	•	Group/condition-aware logic enabled by default

Mode B: Legacy samplesheet
	•	condition column absent
	•	Pipeline sets condition = "NA" (or "default") for all rows
	•	Group/condition-aware logic reduces to legacy behavior

This allows old runs to continue without forcing immediate migration.

1.2 Validation rules

When condition exists:
	•	condition must be non-empty for all non-control samples
	•	replicate must be integer ≥ 1
	•	For each (group, condition) combination:
	•	there must be ≥ 1 replicate (and ideally match existing downstream expectations)

Control matching:
	•	For any target row with control_group = X, the pipeline must find control rows with:
	•	group == X
	•	and either:
	•	condition == target.condition (preferred)
	•	OR (fallback) condition missing on controls or all controls are NA

If neither match exists, fail early with a message that includes:
	•	target sample_id
	•	missing control_group
	•	the expected condition

TODO 2: Group-specific handling for normalization + peak calling

This section defines how group and condition should change pipeline behavior.

2.1 New parameters

Add the following parameters (defaults chosen to preserve current behavior unless condition is provided):

Normalization scope
	•	--normalisation_scope (string; default = all)
	•	all: current behavior (single normalization policy for all samples)
	•	group: compute normalization factors independently per group
	•	group_condition: compute normalization independently per (group, condition)

Notes:
	•	Read-count normalization modes (CPM/BPM/RPKM/None) are inherently per-sample in deepTools, so the scope mainly affects spike-in scaling and any relative scaling logic. The pipeline docs note Spikein is the default normalization mode.  ￼

Control scaling
	•	--igg_scale_scope (string; default = legacy)
	•	legacy: use current --igg_scale_factor behavior (single scalar)
	•	group_condition: compute a per-(group, condition) scaling for controls
	•	sample: compute per-sample scaling using sample/control read counts
	•	--igg_scale_factor stays supported for backwards compatibility (docs already mention it).

Peak calling grouping
	•	--consensus_grouping (string; default = group_condition when condition is present, else group)
	•	group: consensus peaks per group (legacy)
	•	group_condition: consensus peaks per (group, condition) (new)
	•	all: one consensus across all samples (existing “all samples” idea in docs via consensus_peak_mode, keep working)

This aligns with the current doc statement that consensus peaks are merged within “the same experimental group” using bedtools merge.  ￼

2.2 Normalization: group-specific logic

Current behavior (baseline)
The pipeline generates normalized coverage for peak calling / visualization (BigWig outputs exist).  ￼

Required new behavior
If normalisation_scope != all and normalisation_mode == Spikein:
	•	For each scope bucket (group or group_condition):
	1.	Collect spike-in alignment stats for samples in that bucket
	2.	Choose a bucket reference (default = median spike-in mapped reads)
	3.	For each sample in bucket, compute scale factor:
	•	scale_factor = reference_spikein_reads / sample_spikein_reads
	4.	Pass this scale factor into downstream coverage generation and/or bedgraph creation (where spike-in scaling is currently applied)

Design constraints:
	•	No changes to alignment; only to scaling and downstream normalization application.
	•	The scope must not mix different group values unless explicitly requested.

Outputs:
	•	Emit a TSV report per scope bucket:
	•	03_peak_calling/00_normalisation_factors/{scope_id}.tsv
	•	columns: sample_id, group, condition, replicate, spikein_reads, scale_factor, scope_id

Acceptance criterion:
	•	In a run with two groups (e.g., H3K4me3 and H3K27me3), each group gets its own scale-factor set when --normalisation_scope group.

2.3 Peak calling: group- and condition-aware control selection

Peak calling currently supports control usage (unless disabled).

For new callers that require controls (epic2, SPAN/OMNIPEAKS), implement condition-aware pooled IgG generation:

Pooled control definition
For each (control_group, condition) pair:
	•	pool all control replicates for that pair into:
	•	03_peak_calling/01_pooled_controls/{control_group}_{condition}.bam
	•	index .bai

Fallback rules
If there is no control for (control_group, sample.condition):
	1.	If there are controls for the same control_group with other conditions:
	•	use pooled control from the other condition
	•	record this fallback in a QC table
	2.	Else:
	•	if peak caller requires control → skip that caller for that sample with a warning
	•	if peak caller can run without control → run without control and annotate

This matches the “continue on failure + report” philosophy described in the extension spec you provided (peak callers can fail independently).

2.4 Consensus peaks grouping update

Consensus peaks are currently computed by merging replicate peaks of the same experimental group.  ￼
With conditions, “same experimental group” must be defined as:
	•	group_condition by default when condition exists (unless user overrides)

Implementation:
	•	Replace grouping keys used for consensus steps from:
	•	group
to:
	•	group + condition (or a computed group_condition_id)

Output path update (add condition in filenames):
	•	03_peak_calling/05_consensus_peaks/{group}/{condition}/{group}_{condition}_consensus.bed

TODO 3: Add support for additional peak callers

3.1 Supported peak-caller variants

Implement the following variants as first-class options (can be run singly or in combination):

MACS2 (no control; CUT&RUN-optimized)
	•	macs2_narrow
	•	macs2_broad

Defaults (from TODO_PeakCallerExtension.md):
	•	--nomodel --shift -75 --extsize 150 --keep-dup all -q 0.05 --format BAMPE
	•	Broad adds --broad --broad-cutoff 0.1
	•	No control (even if provided)

epic2 (requires pooled control)
	•	epic2_200bp  (window 200, gaps 3, FDR 0.01)
	•	epic2_150bp  (window 150, gaps 2, FDR 0.01)
	•	epic2_25bp   (window 25, gaps 2, FDR 0.01)

Uses pooled control BAM for the sample condition.

SPAN / OMNIPEAKS (requires pooled control)
	•	span_default
	•	span_stringent

Defaults (from TODO_PeakCallerExtension.md):
	•	default: (tool default FDR) gap 5
	•	stringent: FDR 1e-9, gap 2
	•	Java heap default: 8G

GoPeaks (supports narrow default + broad mode)
GoPeaks explicitly supports broad calling via a --broad flag.  ￼
	•	gopeaks_narrow (default)
	•	gopeaks_broad  (--broad)

MultiQC integration detail: MultiQC recognizes *_gopeaks.json and reports peak counts.  ￼
Therefore, the GoPeaks process should emit a JSON summary with this suffix.

3.2 How users select peak callers

Extend existing --peakcaller behavior
Current docs: --peakcaller supports comma-separated values; first is “primary” used downstream, others output-only.

We preserve that behavior and extend the allowed values.

New allowed values (case-insensitive):
	•	Existing: SEACR, MACS2
	•	New:
	•	MACS2_NARROW, MACS2_BROAD
	•	GOPEAKS_NARROW, GOPEAKS_BROAD
	•	EPIC2_200BP, EPIC2_150BP, EPIC2_25BP
	•	SPAN_DEFAULT, SPAN_STRINGENT

Convenience preset (recommended)
Add:
	•	--peakcaller_preset (default = standard)
	•	standard: current default behavior (whatever the pipeline currently defaults to, likely SEACR)
	•	extended: runs the full extension set:
	•	MACS2_NARROW,MACS2_BROAD,GOPEAKS_NARROW,GOPEAKS_BROAD,EPIC2_200BP,EPIC2_150BP,EPIC2_25BP,SPAN_DEFAULT,SPAN_STRINGENT

If both --peakcaller_preset and --peakcaller are provided, --peakcaller wins.

Implementation design: where this fits in the pipeline

4.1 Architectural integration points

The nf-core output docs show distinct stages including:
	•	Sample sheet checking (2.1)
	•	Peak calling (6.x)
	•	Peak-based QC (7.x)  ￼

We will integrate changes into:
	1.	Sample sheet check (parse + validate condition, build metadata objects)
	2.	Normalization / bedgraph / bigwig path (make normalization scope-aware)
	3.	Peak calling subworkflow (add new callers and condition-aware control pooling)
	4.	Consensus peaks + peak QC (use group_condition grouping key when condition exists)

4.2 New / modified modules & subworkflows

A) Samplesheet parsing / validation
	•	Update samplesheet validator (commonly bin/check_samplesheet.py or similar) to:
	•	accept condition
	•	validate control matching rules
	•	generate a normalized “validated samplesheet” artifact used by the pipeline

B) Control pooling process
Add new process:
	•	POOL_IGG_CONTROLS
	•	input: tuples of (control_group, condition, bam, bai)
	•	output: pooled BAM + BAI per (control_group, condition)

C) Peak caller processes (modules)
Create (or import from nf-core modules if available) processes:
	•	MACS2_CALLPEAK_NARROW
	•	MACS2_CALLPEAK_BROAD
	•	EPIC2_CALLPEAK
	•	parameterized by window/gaps variant (or separate modules)
	•	SPAN_OMNIPEAKS_ANALYZE
	•	parameterized by default/stringent
	•	GOPEAKS_CALLPEAK_NARROW
	•	GOPEAKS_CALLPEAK_BROAD

Each should:
	•	take meta map + treatment BAM + optional control BAM (where applicable)
	•	emit:
	•	peaks file (standardized extension)
	•	a version yaml for MultiQC
	•	logs

D) Peak calling orchestrator subworkflow
Create a subworkflow:
	•	PEAK_CALLING_EXTENDED

Responsibilities:
	•	decide which callers to run based on params.peakcaller (expanded list)
	•	build pooled controls channel
	•	run each caller in parallel
	•	collate outputs into a single channel of:
	•	tuple(meta, caller_id, peaks_file)

E) Consensus peaks update
Update existing consensus peaks step to group by:
	•	group_condition_id when condition exists
	•	else fallback to group-only

F) Peak-based QC extension
The pipeline already has peak counts and FRiP outputs (docs list them).  ￼

Update the QC aggregation logic so that QC tables include:
	•	group
	•	condition
	•	caller_id

This enables comparisons across callers and across conditions.

Command defaults (caller-specific)

This section pins defaults (so future changes are intentional & reviewable). For MACS2/epic2/SPAN, use the defaults from TODO_PeakCallerExtension.md.

5.1 MACS2 narrow

macs2 callpeak \
  --nomodel --shift -75 --extsize 150 \
  --keep-dup all \
  -q 0.05 \
  --gsize ${macs2_gsize} \
  --format BAMPE \
  --name ${prefix} \
  --treatment ${treatment_bam}

5.2 MACS2 broad

Same, plus:

--broad --broad-cutoff 0.1

5.3 epic2 variants

epic2 \
  --treatment ${treatment_bam} \
  --control ${pooled_control_bam} \
  --genome ${epic2_genome_name} \
  --window-size <variant> \
  --gaps-allowed <variant> \
  --false-discovery-rate-cutoff 0.01 \
  --output ${prefix}.peaks

Variants:
	•	200bp: window 200, gaps 3
	•	150bp: window 150, gaps 2
	•	25bp:  window 25, gaps 2

5.4 SPAN / OMNIPEAKS

java -Xmx8G -jar ${omnipeaks_jar} analyze \
  -t ${treatment_bam} \
  -c ${pooled_control_bam} \
  --cs ${chrom_sizes} \
  -p ${prefix}

Stringent adds:
	•	--fdr 1.0E-9 --gap 2

5.5 GoPeaks narrow & broad

GoPeaks broad calling uses --broad.  ￼

We implement two variants:
	•	Narrow (default): GoPeaks without --broad
	•	Broad: GoPeaks with --broad

Additionally:
	•	Emit *_gopeaks.json summary so MultiQC can detect peak counts.  ￼

(Exact GoPeaks flags for BAM input/output should be taken from the GoPeaks CLI help at implementation time; the SPEC requirement is that narrow/broad variants exist and differ only by --broad plus any tuned window/step/minwidth parameters you choose to expose as params.)
